Acts as valet key for your car, when you want a valet to park your car but not give him the car key itself, so you give him the valet key that can only do driving.

Three entities in a workflow:

1. Client application
2. Resource
3. OAuth service provider

OAuth Grant Types — Authorization, Implicit (most common)

For authorization, permissions are added in scope, scope is written in plain text, naming system of the scope is different for different OAuth providers

For user data:

- Google might use: scope=openid email profile
- GitHub might use: user or user:email
- Microsoft might use: [User.Read](http://User.Read)

1. When you sign up to an client app using Google or Github, client app prepares an authorization request and redirects to Google.

```
GET /o/oauth2/v2/auth?
response_type=code                                  --//requested code
&client_id=abc123                                   --//client app id
&redirect_uri=https://client.example.com/callback
&scope=contacts.readonly%20profile%20email          --//requested scope
&state=xyz987                                       --//random value to prevent CSRF
Host: accounts.google.com
```

2. You will be forwarded to Google or Github login UI and they will ask if you want to give permission for certain actions. You choose the actions and define the scope.
3. Google/Github will redirects with a authz code and send to the client app.
4. The client’s backend sends a POST request to Google’s token endpoint: The client exchange the code with the token, this is server-to-server connection.

Google validates:

- the code is real
- it was issued to that client
- the redirect URI matches
- the client is allowed to redeem it
- PKCE check passes if used (optional?)

If valid, Google returns tokens.

5. The app uses the token and only able to do the actions that you permitted.

### **OpenID Connect**

When OAuth is used for authn, standardized OpenID Connect scopes are used for more standardized approach.
